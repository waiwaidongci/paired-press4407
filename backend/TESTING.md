# 联合检验测试记录

本目录测试不依赖 PostgreSQL / Redis / 浏览器：数据库使用临时 SQLite，Redis 使用
测试内的内存列表替身（实现 rpush/blpop/incr/expire）。运行方式（在 `backend/` 下）：

```bash
PYTHONPATH=. python -m tests.test_joint
PYTHONPATH=. python -m tests.test_joint_api
PYTHONPATH=. python -m tests.test_worker_loop
```

最近一次本地全量结果：**81 项断言全部通过（58 + 16 + 7，0 失败）**。

## test_joint.py（算法与编排，58 项）
1. 小样本穷举 oracle：3 个存在重叠与缺席的纸批，并集 4 个编号，联合 p 与独立蛮力
   枚举（不走分片代码）逐位一致；验证双侧最大值校正口径、共享符号配置手工核对。
2. n=18/19 枚举与 Monte Carlo 分界；分片区间不重叠、不漏不重、拼满分母；同计划重算
   逐位一致；乱序到达结果一致；单片重复计算输出相同。
3. 12 组随机小样本（2–3 批、2–8 样、随机 25% 缺席）逐一蛮力枚举核对，全部一致。
4. 输入拒绝：空纸批列表、含空纸批、重采样/分片超范围、字段不完整、批内编号重复。
5. 服务层全链路：登记即 queued、每片一条消息、联合分母创建时固定、全片完成后一次性
   发布、结果含校正 p 与各批原始单批 p、纳入/缺席范围、审计动作、发布 p 与 oracle 一致。
6. 重复分片与晚到分片：已存片幂等跳过（返回 False）、乱序完成正常发布、联合分母不变、
   发布后再到达的消息被忽略且结果不变。
7. 崩溃恢复（MC 多片场景）：部分片完成、一片停在 running 时重启，恢复集合精确等于未
   完成分片；恢复后完成且已存片未重计，结果与一次跑成完全相同。
8. 失败无半组：篡改冻结快照后下一片校验失败抛错，整组 failed、result 为空、错误落库，
   后续消息不能“救活”。
9. 发布前崩溃：全片计数已写、发布未提交时重启，恢复逻辑直接汇总已存片完成发布（不重
   计任何分片），产物文件写出。
10. 登记校验：仅选一个纸批、重复纸批、未知参数、分片大小越界均 422。

## test_joint_api.py（HTTP 层，16 项）
TestClient 驱动：未登录 401、观察员 403、单纸批/未知参数 422、正常登记 200 并冻结整组、
联合运行查询/列表/404、驱动分片后 API 发布 completed 且结果结构完整（校正 p、原始单批
p、纳入范围、联合对称假设说明）；overview 同时含 joint_runs 与原 runs/studies；原单批
运行登记与列表接口回归不受影响。

## test_worker_loop.py（双队列 worker，7 项）
worker 重构为 `main()` + 可导入的 `recover_jobs/process_single/process_joint` 后测试：
冷启动恢复把单批与联合分片分别放入两个队列；有限步消费后联合运行一次性发布、单批同时
完成，消费消息数恰为 1+分片数，两类产物文件均写出；重复分片消息不改变已发布结果；
快照篡改后整组 failed 无半组结论。

## 已知边界
- 单 worker 项目；分片“可并发”指分片之间无共享写、可由多个消费者/进程安全领取，
  当前交付仍由同一 worker 顺序消费两个队列。
- Monte Carlo 的规范抽样序列定义为 `(seed, shard_index)` 派生子流按分片序号拼接；
  改变分片大小会改变规范序列（属不同计划），同一计划重跑严格可复现。
- SQLite 仅用于测试，生产仍为 PostgreSQL16；JSON 字段原地变更需 flag_modified，
  服务代码对冻结数据只做整体赋值，不做原地修改。
